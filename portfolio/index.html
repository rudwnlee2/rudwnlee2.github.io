01

재요청에 따른 Kafka 성공 이벤트 중복 생성 방지

문제

발급 완료 후 네트워크 문제로 응답이 유실되면 같은 요청이 다시 들어올 수 있음. 쿠폰은 한 장만 발급돼도 요청마다 성공 이벤트를 만들면 운영 현황의 발급 성공 수가 실제보다 증가

원인

기존 발급 결과에 신규 발급과 DB에 저장된 완료 응답의 재사용을 구분하는 정보가 없어 성공 이벤트 생성 여부를 판단하기 어려움

해결
  • 발급 결과에 replayed 값을 추가해 신규 발급과 완료 응답 재사용을 구분
  • 정책 검증 후 시도 이벤트, 발급 결과 확정 후 결과 이벤트를 Kafka 발행 흐름에 연결. 완료 응답을 재사용한 요청은 성공 이벤트 생성에서 제외
  • 동시 경합 중 완료 응답을 재사용하게 된 경우에도 요청당 시도 이벤트가 한 번만 기록되도록 처리
평가

동일한 요청 식별 키로 3회 요청 시 시도 이벤트 3건, 실제 발급·성공 이벤트 각각 1건 확인. 추가 발급·성공 이벤트 중복 각각 0건, 관련 테스트 83 / 83건 통과

고찰

중복 발급 방지와 별도로, 완료 응답을 재사용한 요청이 성공 집계에 다시 포함되지 않도록 구분 필요. 이번 처리는 애플리케이션의 이벤트 중복 생성을 막는 범위이며 Kafka 전송·재소비 중복 처리는 별도 고려

02

DB 커밋 이후 종료 이벤트를 전파해 다중 서버 지표 동기화

문제

배치 서버에서 회차를 종료해도 각 API 서버는 이를 알 수 없어 종료된 회차의 운영 지표가 각 API 서버 메모리에 남음. DB 반영 전에 이벤트를 보내면 롤백돼도 지표만 먼저 사라질 수 있었음

원인

회차 종료는 배치 서버에서 처리하고 지표는 각 API 서버의 메모리에 저장됨. MySQL 트랜잭션과 Redis 이벤트 발행도 하나의 작업으로 묶을 수 없었음

해결
  • 종료 이벤트를 트랜잭션에 등록하고 DB 커밋 완료 후에만 Redis Pub/Sub으로 발행
  • 이벤트를 수신한 각 API 서버에서 해당 회차의 지표를 제거하고, Redis 구독 실패 시 5초 간격으로 재연결 시도
평가

커밋 전 0건·커밋 후 1건·롤백 후 0건 발행을 확인. Subscriber 2개가 같은 이벤트를 수신하고, 재연결 뒤 신규 이벤트부터 다시 받는 실제 Redis 동작도 검증

고찰

Pub/Sub은 연결이 끊긴 동안의 메시지를 다시 보내지 않음. API 기동 시 최근 24시간 동안 종료된 회차를 최대 1,000개까지 DB에서 다시 조회해 누락된 지표를 정리

03

4개 비교 지표로 Redis·MySQL 불일치 추적

문제

Redis 재고는 줄었지만 DB 발급 이력이 남지 않는 등 저장소가 어긋나도 전체 발급 수만으로는 문제가 생긴 지점을 찾기 어려움

원인

쿠폰 발급 상태가 Redis 재고·누적 발급 수·회원 기록과 DB 발급 이력·재고 카운터에 나뉘어 저장되고, 각 값의 반영 시점도 달랐음

해결
  • Redis와 MySQL에 나뉜 재고·누적 발급·회원 기록·DB 집계를 네 가지 기준으로 대조하는 검증 로직 구현
  • 비교 결과의 차이와 방향을 나누어 우선 확인할 저장소와 처리 구간을 좁히도록 구성
평가

양수·음수 차이, 원천 값 누락, 조회 불가, 오래된 값과 숫자 범위 초과를 테스트. FINAL에서는 네 비교 결과가 모두 0이고 초과 발급이 없을 때만 정상으로 판정

고찰

운영 중에는 Redis와 MySQL의 반영 시점 차이를 허용하되, 처리가 끝난 뒤에는 한 건의 차이도 허용하지 않도록 LIVE와 FINAL의 판정 기준을 분리

01

Redis Lua로 동시 투표 결과 일치

문제

선택 변경을 여러 단계로 나누면 요청이 동시에 들어올 때 개인 선택과 후보별 투표 수가 달라질 가능성

원인

개인 선택 변경과 후보별 투표 수 갱신이 여러 명령으로 나뉘면 동시 요청의 실행 순서에 따라 일부 변경만 반영될 수 있었음

해결
  • 투표 진행 정보를 Redis Hash에 저장하고 상태·마감 시간·후보를 Lua에서 확인
  • 기존 표 차감·새 표 가산·개인 선택 변경을 Redis Lua 한 번으로 처리
평가

개인 선택과 집계를 함께 변경하고 동일 선택은 중복 가산하지 않는 처리 기준 확립. 사용자 40명의 요청에서 총 40표 집계 확인. 선택 변경·동일 선택 재요청·마감 처리를 포함한 Redis 통합 테스트 14개 통과

고찰

진행 중 Redis 데이터가 사라지면 투표를 복구할 수 없음. 보존해야 하는 확정 결과는 마감 후 MySQL에 저장

02

RabbitMQ로 재추천 응답 분리

문제

재추천 요청에서 점수 계산과 외부 AI 호출까지 기다리면 API 응답이 늦어지고, 외부 API 오류가 요청 처리에 직접 영향을 줄 가능성

원인

추천 작업에 점수 계산과 외부 AI 응답 대기가 포함되므로, 재추천 API에서 직접 실행할 경우 작업 완료까지 요청이 대기

해결
  • 방장 권한과 세션 상태를 확인하고, 메뉴 선택 단계에서 후보가 0개·1개인 경우 재추천을 허용하도록 기준 설정
  • 추천 진행 상태로 변경한 뒤 DB 커밋 후 이벤트를 발행해 기존 RabbitMQ 비동기 추천 흐름에 재추천 API를 연결
  • 후보가 없는 추천 진행 상태에서도 재요청을 허용해 중단된 추천을 다시 요청할 경로 마련
평가

모의 AI 응답 지연 3초·초당 2건·Consumer 8개 조건에서 동기 비교 구현 대비 재추천 HTTP 응답 p95를 3,168ms → 64ms로 약 98% 단축. 방식별 100건씩 3회, 총 600건의 결과 저장과 Redis 상태 정합성 확인. HTTP 실패·미완료·결과 불일치 0건

고찰

추천 결과 완료 p95는 양쪽 모두 약 3.17초로 유사하며, 외부 AI 대기를 HTTP 응답에서 분리한 효과. 과거 운영 버전이 아닌 동기 비교 구현과의 통제 실험 결과. DB 커밋 후 메시지 발행 전 요청 누락 가능성은 별도로 남아 있어 Outbox 적용 필요

03

Redis 마감 집계 보존으로 DB 저장 재처리

문제

Redis에서 마감 집계를 만든 뒤 MySQL 저장에 실패했을 때 집계까지 지우면 같은 결과로 재저장 불가

원인

Redis의 마감 집계와 MySQL의 확정 결과가 서로 다른 저장소에 있어 하나의 트랜잭션으로 묶을 수 없었고, 집계를 먼저 지우면 재시도 기준도 사라졌음

해결
  • Redis 마감 집계를 MySQL 저장 성공 전까지 보존해 실패 후 같은 결과로 다시 시도할 기준 마련
  • 저장이 완료된 뒤에만 Redis 집계를 삭제하도록 처리 순서 분리
평가

저장 실패 시 같은 마감 집계로 재시도하고, 이미 저장된 결과는 정리만 재시도하는 기준 확립. DB 저장 실패를 모의한 단위 테스트에서 집계 삭제 미호출과 완료 결과의 중복 저장 방지 검증. 마감·재처리 관련 단위 테스트 9개 통과

고찰

Redis 장애나 TTL 만료로 집계가 사라지면 재처리 기준도 유실. 이를 감지할 운영 지표와 대응 방법 추가 필요
