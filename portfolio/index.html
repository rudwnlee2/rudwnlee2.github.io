01

Redis와 MySQL 간 데이터 불일치 추적

문제

Redis 재고는 줄었지만 DB 발급 이력이 남지 않는 등 저장소가 어긋나도 전체 발급 수만으로는 문제가 생긴 지점을 찾기 어려움

선택과 실행
  • 재고 차감과 실제 발급전체 수량 − Redis 잔여 수량과 DB 활성 쿠폰 수 비교
  • Redis 내부 기록Redis 누적 발급 수와 Redis 발급 회원 수 비교
  • Redis와 DB 발급 이력Redis 누적 발급 수와 DB 누적 발급 이력 비교
  • DB 내부 집계DB 활성 쿠폰 수와 재고 테이블의 활성 발급 수 비교

운영 중인 LIVE에서는 처리 시점에 따른 차이를 확인. 마감 후 FINAL에서는 네 비교 결과가 모두 0이고 초과 발급이 없을 때 정상으로 판정

검증과 한계

차이의 부호로 어느 저장소가 앞섰는지 확인하고, FINAL에서는 모든 차이가 0일 때만 통과. 계산식·누락 값·숫자 범위 초과를 테스트로 확인

02

종료 이벤트 기반 다중 서버 지표 정리

문제

배치 서버에서 쿠폰 회차가 종료돼도 각 API 서버는 이를 알 수 없어 종료된 회차의 Micrometer 지표가 계속 남을 수 있음. DB 반영 전에 이벤트를 보내면 롤백돼도 지표만 먼저 사라질 위험도 존재

선택과 실행

종료 이벤트를 트랜잭션에 등록하고 DB 커밋이 끝난 뒤에만 발행. Redis Pub/Sub으로 모든 API 서버에 전달해 각 서버가 해당 회차의 지표를 제거

sequenceDiagram
    participant Batch as Batch 서버
    participant DB as MySQL
    participant Event as afterCommit
    participant Redis as Redis Pub/Sub
    participant APIs as API 서버들
    Batch->>DB: 쿠폰 회차 종료 반영
    Batch->>Event: 종료 이벤트 등록
    alt DB 커밋
        DB-->>Event: commit 완료
        Event->>Redis: 종료 이벤트 발행
        Redis-->>APIs: 모든 구독 서버에 전파
        APIs->>APIs: 종료 회차 지표 제거
    else DB 롤백
        DB-->>Event: rollback
        Note over Event,Redis: 이벤트 발행 안 함
    end
검증과 한계

커밋 전·롤백 시 이벤트가 나가지 않는지와 여러 API 서버의 수신을 테스트. Pub/Sub은 접속이 끊긴 동안 메시지를 보관하지 않으므로, API 기동 시 최근 종료 회차를 DB에서 다시 조회해 놓친 지표 정리를 보정

Prometheus 조회 실패 격리

문제

쿠폰마다 Prometheus를 따로 조회하면 요청이 계속 늘고, 지표 하나의 실패나 지연 때문에 운영현황 API 전체가 늦어질 수 있음

선택과 실행

여러 쿠폰의 지표를 grouped query로 한 번에 조회하고 평가 시각을 하나로 고정. 발급·고객 결과·지연시간을 나눠 조회하고, 전체 제한 시간을 넘으면 다음 쿼리를 시작하지 않도록 구성

검증과 한계

빈 시계열과 측정값 0, 현재 값과 오래된 값을 구분. 한 영역이 실패해도 나머지는 반환하고 실패한 영역만 UNAVAILABLE로 표시하는 시나리오를 테스트

01

동시 투표 결과 정합성

문제

선택 변경을 여러 단계로 나누면 요청이 동시에 들어올 때 개인 선택과 후보별 투표 수가 달라질 수 있음

선택과 실행

투표 진행 정보는 Redis Hash에 저장. 상태와 마감 시간, 후보를 확인한 뒤 기존 표 차감·새 표 가산·개인 선택 변경을 Lua Script 한 번에 처리

검증과 한계

동시 제출·선택 변경·같은 후보 재선택 테스트에서 개인 선택과 투표 수가 일치. Redis 데이터가 사라지면 진행 중인 투표를 되살릴 수 없어 마감 결과는 MySQL에 저장

02

RabbitMQ 기반 재추천 비동기 처리

문제

재추천 요청에서 점수 계산과 외부 AI 호출까지 바로 실행하면 AI 추천 결과를 기다려야 해 응답이 늦어지고, 외부 API 오류가 사용자 요청에 직접 영향을 줌

선택과 실행

API에서는 후보 수와 세션 상태를 확인하고 MENU_RECOMMENDING으로 변경한 뒤, DB 반영이 끝나면 SurveyRequested를 발행해 기존 RabbitMQ 추천 흐름에 연결. 추천 작업은 Consumer가 이어서 처리

sequenceDiagram
    participant Owner as 방장
    participant Service as FinalMenuSelectionService
    participant DB as MySQL
    participant MQ as RabbitMQ
    participant Worker as 추천 Consumer
    Owner->>Service: 재추천 요청
    Service->>DB: 세션 잠금 및 후보 수 확인
    alt 새 재추천 요청
        Service->>DB: MENU_RECOMMENDING 변경
    else 추천 상태에 멈춘 세션
        Service->>DB: 현재 상태 유지
    end
    DB-->>Service: commit
    Service->>MQ: SurveyRequested 발행
    MQ-->>Worker: 재추천 작업 전달
검증과 한계

API 응답을 장시간 추천 작업과 분리하고, 후보가 0개·1개인 경우와 추천 상태에 멈춘 세션에서 커밋 후 이벤트가 발행되는지 테스트. DB 커밋 직후 메시지 발행 전에 서버가 종료되는 경우까지 막으려면 Outbox 방식이 필요

03

DB 저장 실패 후 재처리

문제

Redis에서 마감 집계를 만든 뒤 MySQL 저장이 실패할 때 집계까지 지우면 같은 결과로 다시 저장할 수 없음

선택과 실행

마감 집계는 Redis에 남겨 두고 MySQL 저장이 끝난 뒤에만 삭제. 저장이 실패하면 남아 있는 집계로 다시 시도

sequenceDiagram
    participant Service as VoteService
    participant Redis as Redis 마감 집계
    participant DB as MySQL
    Service->>Redis: 마감 및 확정 집계 조회
    Redis-->>Service: 마감 집계 반환
    Service->>DB: 결과와 세션 상태 저장
    alt DB 저장 성공
        DB-->>Service: commit
        Service->>Redis: 마감 집계 삭제
    else DB 저장 실패
        DB-->>Service: rollback
        Note over Service,Redis: 마감 집계를 남겨 다시 시도
        Service->>Redis: 남아 있는 마감 집계 조회
        Redis-->>Service: 동일 확정 집계 반환
        Service->>DB: 결과 저장 재시도
    end
검증과 한계

DB 저장 실패 테스트에서 같은 집계로 다시 저장되고, 저장 성공 후에만 Redis 데이터가 삭제됨을 확인. Redis 장애나 TTL 만료로 마감 집계가 유실되는 상황을 탐지할 지표가 필요
