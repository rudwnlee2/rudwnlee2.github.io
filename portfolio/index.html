01

afterCommit과 Redis Pub/Sub으로 종료 지표 동기화

문제

배치 서버에서 쿠폰 회차가 종료돼도 각 API 서버는 이를 알 수 없어 종료된 회차의 Micrometer 지표가 잔존. DB 반영 전에 이벤트를 보내면 롤백돼도 지표만 먼저 사라질 위험

원인

배치 서버와 API 서버가 분리되어 회차 종료 상태가 자동으로 공유되지 않았고, DB 트랜잭션과 이벤트 발행 시점도 연결되어 있지 않았음

해결

종료 이벤트를 트랜잭션에 등록한 뒤 DB 커밋 완료 후에만 Redis Pub/Sub으로 발행. 모든 API 서버는 이벤트를 받아 해당 회차의 지표를 제거합니다.

평가

커밋 전과 롤백 시에는 이벤트가 발행되지 않고, 커밋 후에는 모든 API 서버가 수신하는지 테스트로 확인

고찰

Pub/Sub은 연결이 끊긴 동안 메시지를 보관하지 않음. API 기동 시 최근 종료 회차를 DB에서 다시 조회해 누락된 지표를 정리하도록 보정

02

Grouped Query와 부분 응답으로 Prometheus 실패 격리

문제

쿠폰마다 Prometheus를 따로 조회하면 요청 수가 늘고, 지표 하나의 실패나 지연 때문에 운영현황 API 전체가 늦어질 가능성

원인

쿠폰별 개별 쿼리가 요청 수를 늘렸고, 발급·고객 결과·지연시간 조회가 하나의 성공 응답에 묶여 일부 실패가 전체 응답에 영향을 줬음

해결

여러 쿠폰 지표를 Grouped Query로 묶고 영역별 제한 시간을 적용. 발급·고객 결과·지연시간을 나눠 조회하고 전체 제한 시간을 넘으면 다음 쿼리를 시작하지 않습니다.

평가

한 영역이 실패해도 나머지 결과를 반환하고 실패 영역만 UNAVAILABLE로 표시. 빈 시계열·측정값 0·현재 값·오래된 값의 구분은 시나리오 테스트로 확인

고찰

값이 없다는 사실과 실제 측정값이 0인 상태를 구분해야 운영자가 정상 상태로 오해하지 않습니다. 오래된 값도 별도 상태로 드러내도록 기준을 나눴습니다.

03

4개 비교 지표로 Redis·MySQL 불일치 추적

문제

Redis 재고는 줄었지만 DB 발급 이력이 남지 않는 등 저장소가 어긋나도 전체 발급 수만으로는 문제가 생긴 지점을 찾기 어려움

원인

쿠폰 발급 상태가 Redis 재고·누적 발급 수·회원 기록과 DB 발급 이력·재고 카운터에 나뉘어 저장되고, 각 값의 반영 시점도 달랐음

해결

Redis와 MySQL에 흩어진 발급 상태를 대조하는 정합성 검증 로직을 구현. 전체 발급 수만 확인하지 않고, 불일치가 발생한 저장소와 처리 단계를 구분할 수 있도록 구성

평가

LIVE에서는 처리 중 생긴 차이와 앞선 저장소를 표시하고, FINAL에서는 네 비교 결과가 모두 0이고 초과 발급이 없을 때만 정상으로 판정. 계산식·누락 값·숫자 범위 초과는 테스트로 확인

고찰

운영 중에는 저장소별 반영 시점이 달라 일시적인 차이가 발생. 이를 장애로 잘못 판단하지 않도록 LIVE와 FINAL의 기준을 분리

01

Redis Lua로 동시 투표 결과 일치

문제

선택 변경을 여러 단계로 나누면 요청이 동시에 들어올 때 개인 선택과 후보별 투표 수가 달라질 가능성

원인

개인 선택 변경과 후보별 투표 수 갱신이 여러 명령으로 나뉘면 동시 요청의 실행 순서에 따라 일부 변경만 반영될 수 있었음

해결

투표 진행 정보를 Redis Hash에 저장하고, 상태·마감 시간·후보 확인과 기존 표 차감·새 표 가산·개인 선택 변경을 Redis Lua 한 번으로 처리.

평가

동시 제출·선택 변경·같은 후보 재선택에서도 개인 선택과 후보별 투표 수가 일치하는지 테스트로 확인

고찰

진행 중 Redis 데이터가 사라지면 투표를 복구할 수 없음. 보존해야 하는 확정 결과는 마감 후 MySQL에 저장

02

RabbitMQ로 재추천 응답 분리

문제

재추천 요청에서 점수 계산과 외부 AI 호출까지 바로 실행하면 AI 추천 결과를 기다리는 동안 API 응답이 늦어지고, 외부 API 오류가 사용자 요청에 직접 영향을 줬습니다.

원인

점수 계산과 외부 AI 호출처럼 오래 걸리는 작업이 재추천 요청 흐름에 포함되어 API가 추천 완료까지 기다리는 구조였음

해결

API는 후보 수와 세션 상태를 확인해 MENU_RECOMMENDING으로 바꾸고, 커밋 후 SurveyRequested를 발행해 RabbitMQ 추천 Consumer에 작업을 전달.

평가

API 응답과 장시간 추천 작업을 분리하고, 후보 0개·1개와 추천 상태에 멈춘 세션의 재요청을 테스트로 확인

고찰

DB 커밋 직후 메시지를 발행하기 전에 서버가 종료되면 요청이 누락될 수 있습니다. 이 구간까지 보완하려면 Outbox 적용이 필요합니다.

03

Redis 마감 집계 보존으로 DB 저장 재처리

문제

Redis에서 마감 집계를 만든 뒤 MySQL 저장이 실패할 때 집계까지 지우면 같은 결과로 다시 저장할 수 없었습니다.

원인

Redis의 마감 집계와 MySQL의 확정 결과가 서로 다른 저장소에 있어 하나의 트랜잭션으로 묶을 수 없었고, 집계를 먼저 지우면 재시도 기준도 사라졌음

해결

Redis 마감 집계를 MySQL 저장 성공 전까지 보존하고, 저장 실패 시 남은 집계로 다시 시도. 저장 성공 후에만 Redis 집계를 삭제합니다.

평가

DB 저장 실패 후에도 같은 집계로 재저장되고 성공 후에만 삭제되는지 테스트로 확인

고찰

Redis 장애나 TTL 만료로 마감 집계가 사라지는 상황은 별도로 감지해야 합니다. 집계 유실을 확인할 운영 지표가 추가로 필요합니다.
