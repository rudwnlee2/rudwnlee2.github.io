쿠폰 야호

한정 수량 쿠폰을 정확하게 발급하고, 순간 트래픽의 처리 과정과 운영 상태를 관찰할 수 있도록 만든 선착순 쿠폰 플랫폼입니다.

프로젝트 목적

요청이 한순간에 몰리는 상황에서도 정해진 수량만 발급하고, 사용자 대기부터 발급 결과까지의 흐름을 운영자가 확인할 수 있는 시스템을 목표로 했습니다.

담당 범위

관리자 운영현황

발급 흐름, 대기열, 재고 위험, 고객 결과를 하나의 운영 응답으로 조립했습니다.

상태 계약

수집 중이거나 사용할 수 없는 데이터를 정상값과 구분하는 상태 모델을 정의했습니다.

계산 책임 분리

재고 위험도와 권장 조치를 독립 계산기로 분리해 규칙을 명시적으로 관리했습니다.

계약 테스트

Core·API·Prometheus 경계에서 상태와 응답 의미가 유지되는지 검증했습니다.

핵심 문제

DB, Prometheus, 대기열 데이터는 서로 다른 시점에 준비됩니다. 일부 데이터가 아직 없거나 수집에 실패했을 때 기본값을 채우면, 운영자는 불완전한 정보를 정상 상태로 오해할 수 있었습니다.

기술적 선택

값과 데이터 상태를 함께 전달

값만 반환하는 대신 VALID·PENDING·UNAVAILABLE 상태를 함께 전달하고, 전체 응답에는 PARTIAL을 표현하도록 설계했습니다.

조립과 판단 책임을 분리

서비스는 여러 데이터 소스를 조립하고, 위험도와 권장 조치 같은 정책 판단은 독립 계산기가 담당하도록 나눴습니다. 새로운 지표가 추가돼도 계산 규칙을 개별적으로 검증할 수 있습니다.

구현

Client→Queue→Coupon API→Redis · MySQL→Kafka

AdminOverviewService가 저장소와 관측 데이터에서 발급·대기·재고 정보를 수집하고, 각 계산기의 결과를 운영현황 응답으로 조립합니다. 데이터가 준비되지 않은 경우에는 값을 추측하지 않고 상태와 권장 조치로 드러냅니다.

검증

Core 계약

경계값과 데이터 조합에 따라 계산 결과와 상태가 올바르게 전이되는지 확인했습니다.

API 계약

운영현황 응답 구조와 상태 의미가 직렬화 이후에도 유지되는지 검증했습니다.

Prometheus 경계

지표의 정상 수집, 대기, 사용 불가 상황을 분리해 처리하는지 확인했습니다.

실패 가시성

일부 데이터 실패가 전체 성공으로 감춰지지 않고 PARTIAL로 노출되는지 검증했습니다.

결과 및 회고

운영자는 단일 숫자만 보는 대신 해당 데이터가 신뢰 가능한지 함께 판단할 수 있게 됐습니다. 수집 실패를 예외 처리의 세부사항으로 숨기지 않고 API 계약에 포함한 것이 핵심입니다. 이후에는 실제 부하 구간별 기준값을 축적해 위험도 계산의 근거를 더 정교하게 만드는 것이 과제로 남아 있습니다.
