갈래말래

그룹원의 조건을 반영해 메뉴 후보를 추천하고, 실시간 투표를 통해 최종 결정을 돕는 그룹 의사결정 서비스입니다.

5인 팀팀장투표 도메인 담당
GitHub ↗처리 흐름 보기

프로젝트 목적

여러 사람이 함께 메뉴를 고를 때 반복되는 의견 수집과 결정을 줄이기 위해, 조건 기반 추천과 실시간 투표를 하나의 흐름으로 연결했습니다.

담당 범위

팀 리딩

기능 범위와 일정, 도메인 간 책임을 조율하고 투표 흐름을 중심으로 개발을 진행했습니다.

투표 상태 모델

투표 생성, 진행, 마감과 선택 변경 시 발생할 수 있는 상태 전이를 정의했습니다.

동시성 처리

Redis Hash와 Lua Script를 이용해 기존 선택 차감과 새 선택 가산을 묶었습니다.

실시간 알림

STOMP 구독 경계를 설정하고 투표 변경 내용을 참여자에게 전달했습니다.

핵심 문제

여러 사용자가 동시에 투표하거나 선택을 변경하고, 같은 시점에 투표가 마감될 수 있습니다. 어떤 순서로 요청이 도착하더라도 사용자 선택과 후보별 집계가 일치해야 했습니다.

기술적 선택

Redis Lua로 복합 변경을 원자화

애플리케이션에서 조회와 변경을 나누지 않고, 기존 선택 차감·새 선택 가산·마감 여부 검증을 하나의 Redis Lua 실행으로 처리했습니다.

REST와 STOMP의 역할 분리

투표 상태 조회와 변경은 REST를 기준으로 삼고, STOMP는 변경 사실을 빠르게 알리는 역할에 집중시켰습니다. 알림 누락이 상태 자체의 손실로 이어지지 않도록 한 선택입니다.

구현

Client→REST API→Redis Lua→MySQL
└→ STOMP 알림

Redis Hash에 사용자별 선택과 후보별 집계를 관리하고, Lua Script 안에서 현재 상태 확인과 집계 변경을 연속으로 수행합니다. 처리 후 발생한 변경은 STOMP로 알리며, 클라이언트는 필요할 때 REST에서 기준 상태를 다시 조회합니다.

검증

상태 전이

진행 중 변경과 마감 이후 요청이 정의한 규칙대로 처리되는지 확인했습니다.

선택 변경 정합성

기존 후보 차감과 새 후보 가산 결과가 사용자 선택과 일치하는지 검증했습니다.

API 응답

투표 결과와 오류 상황이 클라이언트가 구분할 수 있는 계약으로 반환되는지 확인했습니다.

구독 권한

허용된 참여자만 투표 채널을 구독하고 변경 알림을 받을 수 있는지 검증했습니다.

결과 및 회고

선택 변경을 여러 명령으로 분리하지 않고 하나의 원자 연산으로 묶어, 사용자 선택과 후보별 집계가 함께 변경되는 경계를 명확히 했습니다. 또한 실시간 전송을 기준 데이터와 분리해 연결 상태가 불안정해도 REST를 통해 현재 상태를 복구할 수 있도록 했습니다. 이후에는 실제 동시 요청 규모를 기준으로 부하 테스트와 재연결 시나리오를 더 확장할 수 있습니다.
